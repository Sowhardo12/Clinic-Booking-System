**Status Legend:**
- **Verified** — behavior confirmed against implementation via code inspection (automated test not yet written)
- **Unclear** — behavior ambiguous, needs code inspection or product decision
- **Not implemented** — test exists but not yet written for this feature
- **Not tested** — feature identified, no automated test exists yet AND behavior has not been confirmed via code inspection

**Separation Note:** `Verified` reflects that the implementation was inspected and the behavior matches the documented scenario (e.g., `FOR UPDATE` locking, idempotency key processing). `Not tested` means no automated test has been written — the behavior may still be correctly implemented. These two statuses are independent: a feature can be `Verified` (inspected) but still `Not tested` (no automated test).

**Notes:**
- All statuses start as `Not tested` because this skill does not execute tests; it only maps the testing landscape.
- The "Implementation Evidence" column references the exact file and method that contains the logic for each scenario.
- Critical / High priority items correspond to booking correctness, data integrity, and idempotency — these should be the first test targets.
- The N+1 vs optimized admin endpoints are documented behavior (metrics logged by the service), not API guarantees, so their test layer is E2E with logged metric verification.
- Concurrency functional invariant (FOR UPDATE prevents double-booking) is marked as a critical integration/concurrency test that must assert database state, not k6 throughput.
